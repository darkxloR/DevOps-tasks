# Training App — GitLab CI/CD

Приложение из предыдущего задания, развёрнутое через автоматический пайплайн. Push в `main` запускает тесты, сборку образа и деплой на учебный сервер.

---

## Pipeline

```
git push
   ↓
[test]    прогон автотестов
   ↓
[build]   сборка Docker-образа
   ↓
[deploy]  выкатка на сервер (вручную)
```

Три этапа объявлены в начале `.gitlab-ci.yml`:

```yaml
stages:
  - test
  - build
  - deploy
```

**Порядок здесь — не оформление, а механизм защиты.** Этапы выполняются последовательно; провал одного останавливает всю цепочку. Это проверено на практике: при намеренно сломанном тесте `build-image` и `deploy` получили статус **Skipped** — сломанный код физически не дошёл ни до сборки, ни до сервера.

### Stage: test

```yaml
run-tests:
  stage: test
  image: python:3.12-slim
  services:
    - postgres:16
  variables:
    POSTGRES_DB: appdb
    POSTGRES_USER: appuser
    POSTGRES_PASSWORD: $DB_PASSWORD
    DB_HOST: postgres
    DB_NAME: appdb
    DB_USER: appuser
    BASE_URL: http://localhost:9000
  script:
    - pip install pytest requests psycopg2-binary
    - python3 app/app.py > app.log 2>&1 &
    - sleep 5
    - cat app.log
    - pytest tests/ -v
```

**Что здесь происходит.** Раннер поднимает контейнер `python:3.12-slim`, рядом с ним контейнер `postgres:16`, клонирует репозиторий, ставит зависимости, запускает приложение в фоне и прогоняет тесты.

| Ключ | Назначение |
|---|---|
| `image` | образ, внутри которого выполняется `script` |
| `services` | дополнительные контейнеры рядом с задачей; доступны по имени образа — отсюда `DB_HOST: postgres` |
| `variables` | переменные окружения задачи |
| `script` | команды по порядку; первая с ненулевым кодом возврата проваливает задачу |

**`python3 app/app.py &`** — амперсанд отправляет процесс в фон. Без него `serve_forever()` заблокировал бы выполнение, и до тестов дело бы не дошло.

**`> app.log 2>&1` и `cat app.log`** добавлены после отладки. Фоновый процесс теряет вывод: если приложение падает при старте, `script` молча идёт дальше, а тесты валятся с `Connection refused` — без указания причины. Перенаправление в файл и вывод его **до** запуска тестов делают причину видимой в логе задачи.

Порядок важен: `cat` стоит перед `pytest`. Поставить после — и при падении тестов до него не дойдёт, ровно тогда, когда он нужнее всего.

**`BASE_URL`** вынесен в переменную, потому что в пайплайне nginx нет: приложение запускается напрямую и слушает 9000, а локально проверяется через прокси на 8080.

### Stage: build

```yaml
build-image:
  stage: build
  image: docker:27
  services:
    - docker:27-dind
  variables:
    DOCKER_HOST: tcp://docker:2375
    DOCKER_TLS_CERTDIR: ""
  script:
    - docker build -t training-app:$CI_COMMIT_SHORT_SHA app/
    - docker images
```

**Проблема, которую это решает.** Задача сама выполняется внутри контейнера, а должна собрать другой контейнер. Docker внутри контейнера по умолчанию недоступен — там нет ни клиента, ни демона.

**Docker-in-Docker.** Рядом поднимается контейнер `docker:27-dind` с полноценным демоном, а задача работает как клиент:

| Переменная | Смысл |
|---|---|
| `image: docker:27` | Docker CLI, клиент без демона |
| `services: docker:27-dind` | контейнер с демоном, доступен по имени `docker` |
| `DOCKER_HOST: tcp://docker:2375` | клиент по умолчанию ищет Unix-сокет локально; здесь демон в соседнем контейнере, нужен TCP |
| `DOCKER_TLS_CERTDIR: ""` | отключает TLS; для учебной задачи упрощает настройку, в production так не делают |

**`app/`** в конце команды — контекст сборки, каталог с Dockerfile.

### Stage: deploy

```yaml
deploy:
  stage: deploy
  when: manual
  tags:
    - linux
  script:
    - docker compose down
    - docker compose up -d --build
    - sleep 10
    - curl -f http://localhost:8080/health
```

**Нет ключа `image`** — задача выполняется на раннере с executor `shell`, то есть команды идут прямо на сервере. Контейнер не нужен.

**`tags: - linux`** обязателен. Без метки задача может уйти на общие раннеры GitLab, где целевого сервера не существует. Метка направляет её строго на раннер, установленный на `intern-srv-l2`.

**`curl -f`** — проверка результата деплоя. Флаг заставляет curl вернуть ненулевой код при ответе 4xx/5xx. Приложение не поднялось — задача падает, и это видно сразу, а не при следующем обращении пользователя.

**`when: manual`** — разбор ниже.

## Trigger

Пайплайн запускается **автоматически при каждом push** в репозиторий. Отдельной настройки это не требует: GitLab запускает пайплайн, если в корне есть файл `.gitlab-ci.yml`.

Проверено: каждый `git push` создавал новый пайплайн, привязанный к конкретному коммиту.

**Этап `deploy` при этом не выполняется сам** — из-за `when: manual` он создаётся в состоянии ожидания. Пайплайн получает статус `blocked`, пока кто-то не нажмёт запуск.

## Docker Image

**Сборка:**

```bash
docker build -t training-app:$CI_COMMIT_SHORT_SHA app/
```

**Тег — идентификатор коммита.** Переменная `CI_COMMIT_SHORT_SHA` предоставляется GitLab автоматически и содержит 8 символов SHA:

```
CI_COMMIT_SHA=7984be98f7beef564b37884212e9550fc1612aed   ← 40 символов
CI_COMMIT_SHORT_SHA=7984be98                             ← 8 символов
```

Список доступных переменных выводился прямо в пайплайне командой `env | grep CI_COMMIT | sort` — быстрее, чем искать в документации, и сразу с реальными значениями. Рядом обнаружились `CI_COMMIT_BRANCH`, `CI_COMMIT_MESSAGE`, `CI_COMMIT_AUTHOR` и другие.

### Почему не `latest`

**Старый образ теряет имя.** Docker снимает тег `latest` со старого образа и вешает на новый. Старый не удаляется, но остаётся безымянным — в `docker images` он виден как `<none>`.

Обратиться к нему можно только по ID, который надо было записать заранее. Никто не записывает. А `docker image prune` со временем подчистит безымянные образы, и возвращаться будет некуда.

**Версия перестаёт быть определённой.** На вопрос «что сейчас в проде» ответ «latest» не значит ничего. С тегом `7984be98` открываешь этот коммит в GitLab и видишь точный код.

**Обманчивая идентичность.** Два сервера могут держать образы с одинаковым тегом `latest`, но разным содержимым — один тянул вчера, другой сегодня. Формально версия одна, фактически разные.

**Откат с нормальными тегами:**

```bash
docker run training-app:7984be98    # предыдущая, рабочая
```

Оба образа существуют, у обоих есть имена, каждое ведёт к конкретному коммиту.

## Deployment

### Архитектура

Сервер `intern-srv-l2` находится в частной сети университета и не имеет публичного адреса. Облачные раннеры GitLab до него достучаться не могут: NAT пропускает исходящие соединения, но не входящие.

**Направление перевёрнуто.** На сервере установлен собственный GitLab Runner, который сам подключается к gitlab.com и опрашивает: есть ли работа. Получив задачу, выполняет её локально.

```
gitlab.com  ←── исходящее соединение ──  intern-srv-l2 (runner)
```

Ни проброса портов, ни открытого наружу SSH.

**Побочная выгода:** раннер уже на целевой машине. Деплой сводится к обычным командам `docker compose`, ключи и SSH не нужны вовсе.

### Конфигурация раннера

| Параметр | Значение |
|---|---|
| Тип | project runner |
| Executor | `shell` |
| Метка | `linux` |
| Run untagged jobs | да |
| Конфиг | `/etc/gitlab-runner/config.toml` |

**Executor `shell`** выбран потому, что задача должна управлять контейнерами **на сервере**. С executor `docker` команды ушли бы внутрь временного контейнера и до хоста не добрались.

**Регистрация системная**, а не пользовательская. Первая попытка выполнялась без `sudo`, и конфигурация легла в `~/.gitlab-runner/config.toml` — туда, куда системный сервис не смотрит. Раннер числился зарегистрированным, но задач не получал.

Проверяется так:
```bash
sudo gitlab-runner list    # ConfigFile=/etc/gitlab-runner/config.toml
gitlab-runner list         # ConfigFile=/home/USER/.gitlab-runner/config.toml
```

**Доступ к Docker.** С executor `shell` задачи выполняются от пользователя `gitlab-runner`, созданного пакетом. Ему нужно членство в группе `docker`:

```bash
sudo usermod -aG docker gitlab-runner
sudo systemctl restart gitlab-runner
```

Осознанный компромисс: членство в группе `docker` фактически равнозначно root, поскольку через монтирование хостовой файловой системы в контейнер можно получить полный доступ. Для раннера, управляющего контейнерами, это неизбежно; в production применяют более узкие механизмы.

### Процесс

```bash
docker compose down          # остановить текущую среду
docker compose up -d --build # пересобрать и поднять
sleep 10                     # дать приложению время
curl -f http://localhost:8080/health   # проверить
```

Раннер клонирует репозиторий в свой рабочий каталог (`/home/gitlab-runner/builds/...`) и выполняет команды там.

**Замечание о совпадении имён проектов.** Compose определяет имя проекта по имени каталога. Каталог раннера и рабочий каталог разработчика называются одинаково — `traning-app-ci`, — поэтому с точки зрения Docker это **один и тот же проект**. Деплой пересоздаёт ту же среду, а не поднимает вторую.

Для учебной задачи приемлемо, но при переносе схемы стоит либо задавать имя проекта явно (`COMPOSE_PROJECT_NAME`), либо деплоить в фиксированный каталог через `git pull`.

## Secrets

**В репозитории секретов нет.** `.gitignore` создан до первого коммита — это принципиально: попавший в историю git секрет остаётся в старых коммитах, и удаление требует переписывания истории.

```
.env
*.log
__pycache__/
*.pyc
```

Проверка перед коммитом:

```bash
git status --untracked-files=all
```

Флаг `--untracked-files=all` раскрывает каждый файл по отдельности; без него git показывает новый каталог одной строкой, и содержимое не видно.

В репозиторий коммитится `.env.example` — структура без значений:

```
DB_NAME=appdb
DB_USER=appuser
DB_PASSWORD=changeme
```

### Где хранятся реальные значения

**GitLab CI/CD Variables** — Settings → CI/CD → Variables:

| Key | Masked | Назначение |
|---|---|---|
| `DB_NAME` | нет | имя базы, не секрет |
| `DB_USER` | нет | логин, без пароля бесполезен |
| `DB_PASSWORD` | **да** | пароль |

**Masked** скрывает значение в логах задач, заменяя на `[MASKED]`. Требования GitLab к маскируемым значениям: минимум 8 символов, без пробелов и переводов строк. Именно поэтому `appdb` и `appuser` маскировать нельзя — короткие; впрочем, и не нужно.

**Переменные проекта автоматически попадают в окружение задачи**, а Compose читает переменные окружения так же, как из файла `.env`. Дополнительных действий не требуется: `${DB_PASSWORD}` в `docker-compose.yml` подставится из настроек GitLab.

### Урок про утечки

Токен раннера дважды был опубликован в переписке при копировании вывода `gitlab-runner list` — строка содержит его целиком. Оба раза раннер пересоздавался.

Токен даёт право забирать задачи проекта и читать переменные CI, включая пароли. Утечка через переписку, скриншот или лог ничем не лучше утечки через git.

Практический вывод: при выводе диагностических команд смотреть, что именно копируешь.

## Manual Deployment

```yaml
deploy:
  when: manual
```

Задача создаётся, но остаётся в состоянии ожидания. Пайплайн получает статус `blocked` до явного нажатия кнопки запуска.

### Зачем ручное подтверждение, если тесты прошли

**Тесты покрывают только то, что в них написано.** В проекте их три: два эндпоинта и обработка неизвестного пути. Всё остальное поведение не проверяется вообще — производительность, нагрузка, интеграция со смежными системами, миграции.

**Тесты проверяют поведение, а не содержимое.** Приложение с захардкоженным паролем ведёт себя ровно как правильное — все проверки зелёные. Обнаружить такое может только человек на review или отдельный сканер. Это показывает границу автоматизации.

**Момент выкатки — отдельное решение.** Пятница вечером, час пик, идёт мероприятие. Код исправен, выкатывать сейчас не стоит.

**Согласованность с другими изменениями.** Новая версия может требовать миграции базы или обновления смежного сервиса; порядок операций важен и автоматике не известен.

**Продуктовое решение.** Функция работает технически, но команда решает не выпускать её сейчас.

**Ответственность.** Без ручного шага любой merge в `main` уезжает в продакшен. Ручное подтверждение делает выкатку осознанным решением конкретного человека, а не побочным эффектом слияния ветки.

## Troubleshooting

### Приложение не запускалось в тестах: Connection refused

**Симптом.** Все три теста упали одинаково:

```
requests.exceptions.ConnectionError: HTTPConnectionPool(host='localhost', port=9000):
Failed to establish a new connection: [Errno 111] Connection refused
```

**Первое наблюдение.** `Connection refused` означает, что на порту никто не слушает. То есть сломаны не тесты — тестировать нечего, приложение не поднялось.

**Почему причина была не видна.** Приложение запускалось командой `python3 app/app.py &`, и вывод фонового процесса терялся. Упало оно при старте или нет — из лога задачи понять было нельзя.

**Корневая причина.** Пароль. В задаче было прописано:

```yaml
POSTGRES_PASSWORD: testpass    # база создавалась с этим
DB_PASSWORD: testpass          # приложение подключалось с этим
```

После добавления `DB_PASSWORD` в переменные проекта возник конфликт: **переменные проекта имеют приоритет** над объявленными в задаче. База поднималась со старым `testpass`, приложение пыталось подключиться с новым значением.

**Исправление:**

```yaml
POSTGRES_PASSWORD: $DB_PASSWORD    # оба берут одно значение
                                    # строка DB_PASSWORD: testpass удалена
```

**Плюс устранена слепота:**

```yaml
- python3 app/app.py > app.log 2>&1 &
- sleep 5
- cat app.log        ← ДО запуска тестов
- pytest tests/ -v
```

### Деплой падал с exit status 22

**Симптом.** Контейнеры поднимались, postgres доходил до `Healthy`, а задача падала:

```
curl: (22) The requested URL returned error: 502
ERROR: Job failed: exit status 22
```

**Что означает код.** 22 — код возврата curl при ответе 4xx/5xx, следствие флага `-f`. Проверка сработала как задумано: приложение не отвечало, и деплой был признан неуспешным.

**Диагностика на сервере:**

```bash
docker ps -a | grep traning
docker logs traning-app-ci-app-1 --tail 20
```

```
traning-app-ci-app-1   Exited (1)

psycopg2.OperationalError: connection to server at "postgres" (172.18.0.2),
port 5432 failed: FATAL:  password authentication failed for user "appuser"
```

**Третий вид ошибки подключения.** За время работы встретились все три, и по тексту сразу видно стадию сбоя:

| Сообщение | Что произошло |
|---|---|
| `could not translate host name` | контейнер не запущен, DNS-записи нет |
| `Connection refused` | контейнер работает, сервис внутри не слушает порт |
| `password authentication failed` | сервис отвечает, но отвергает учётные данные |

**Корневая причина.** Том `pgdata` создавался, когда пароль был `changeme`. PostgreSQL применяет `POSTGRES_PASSWORD` **только при первой инициализации на пустом томе**. Команда `docker compose down` том не удаляет, поэтому база продолжала ждать старый пароль.

**Исправление:**

```bash
docker compose down -v    # -v уничтожает том
```

После пересоздания база инициализировалась с актуальным паролем, деплой прошёл.

**Вывод на будущее.** Смена пароля базы требует пересоздания тома. В деплое использовать `down -v` нельзя — это уничтожало бы данные при каждой выкатке. Пароль меняется отдельной процедурой с миграцией, а не мимоходом.

### Раннер не получал задачи

**Симптом.** Задача `deploy` висела в статусе `Pending`, хотя раннер числился зарегистрированным.

**Две причины, обнаруженные последовательно:**

**Пользовательская регистрация вместо системной.** Команда `gitlab-runner register` выполнялась без `sudo`, конфиг лёг в `~/.gitlab-runner/config.toml`. Системный сервис читает `/etc/gitlab-runner/config.toml` и работал вхолостую.

**Отсутствие метки.** У задачи стоит `tags: - linux`, значит взять её может только раннер с такой меткой. При пересоздании раннера метка не была указана в веб-форме.

## Изменения в приложении

Для этого задания приложение из предыдущей работы потребовало двух правок.

### Обработка неизвестных путей

Раньше `do_GET` содержал две ветки: `/health` и `else`. Любой неизвестный путь попадал во вторую и получал 200 — возвращать 404 было неоткуда.

**Мешал порядок операций:**

```python
def do_GET(self):
    self.send_response(200)    ← код отправлялся СРАЗУ
    self.end_headers()
    if self.path == "/health":
```

`send_response` пишет строку статуса в сокет немедленно; после этого изменить код невозможно.

**Метод перестроен:** сначала определяется, что отвечать, потом отправляется.

```python
def do_GET(self):
    if self.path == "/health":
        code = 200
        body = ...
    elif self.path == "/":
        code = 200
        body = ...
    else:
        code = 404
        body = "Not Found\n"

    self.send_response(code)
    self.end_headers()
    self.wfile.write(body.encode())
```

Три ветки, отправка одна — после всех проверок.

### Healthcheck для базы

Без него приложение стабильно падало при старте среды: `depends_on` дожидается **запуска** контейнера, а не готовности сервиса. PostgreSQL несколько секунд инициализирует кластер и только потом открывает порт.

Локально это давало три перезапуска и ручное вмешательство. В пайплайне, где среда создаётся с нуля каждый раз, стало бы постоянной проблемой — тесты падали бы через раз без видимой причины. Это худший вид сбоев: непредсказуемые и невоспроизводимые.

```yaml
  postgres:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER}"]
      interval: 5s
      timeout: 3s
      retries: 5

  app:
    depends_on:
      postgres:
        condition: service_healthy
```

**`pg_isready`** — утилита из образа PostgreSQL, возвращает 0 когда сервер принимает соединения.

**Двойной `$$`** нужен, чтобы Compose не подставил переменную сам, а передал символ `$` внутрь контейнера.

**`CMD-SHELL`**, а не `CMD` — команда содержит подстановку переменной, разворачивать её должна оболочка.

**Результат** виден в выводе `docker compose up`:

```
Container postgres-1  Healthy    6.0s
Container app-1       Started    6.0s
```

Раньше оба стартовали мгновенно, и приложение падало. Теперь Compose ждёт готовности базы.

## Tests

```python
import requests
import os

BASE_URL = os.environ.get("BASE_URL", "http://localhost:8080")

def test_root():
    r = requests.get(f"{BASE_URL}/")
    assert r.status_code == 200

def test_health():
    r = requests.get(f"{BASE_URL}/health")
    assert r.status_code == 200
    assert "Application: OK" in r.text

def test_404():
    r = requests.get(f"{BASE_URL}/qwerty")
    assert r.status_code == 404
    assert "Not Found" in r.text
```

**Соглашения pytest:** файлы называются `test_*.py`, функции `test_*`. Регистрировать ничего не нужно, pytest находит их сам.

**Отдельные функции, а не одна с тремя проверками.** При падении видно, какой именно эндпоинт сломался: `test_root PASSED`, `test_health FAILED`. Свалив всё в один тест, локализацию потеряешь.

**`BASE_URL` через переменную окружения.** Локально приложение доступно через nginx на 8080, в пайплайне — напрямую на 9000. Тест не должен быть привязан к одному адресу.

### Проверка падения

Задание требует убедиться, что упавший тест роняет пайплайн. В `test_404` ожидаемый код временно заменён на 200:

```
tests/test_app.py::test_404 FAILED

>       assert r.status_code == 200
E       assert 404 == 200
E        +  where 404 = <Response [404]>.status_code

1 failed, 2 passed
ERROR: Job failed: exit code 1
```

**За что ценен pytest.** Он разбирает выражение и показывает фактические значения: видно, что сравнивалось, где и почему не сошлось. Голый `assert` в обычном скрипте дал бы только `AssertionError`.

**`exit code 1`** — то число, по которому GitLab судит об исходе. Ноль означает успех, любое другое — провал.

**Следствие в интерфейсе:** `build-image` и `deploy` получили статус **Skipped**. Сломанный код не дошёл ни до сборки, ни до сервера.

После восстановления теста — `3 passed`, пайплайн зелёный.

## Final Questions

**1. Что такое CI?**

Continuous Integration — непрерывная интеграция. Практика, при которой изменения от разработчиков часто вливаются в общую ветку, и каждое вливание автоматически проверяется: сборка, тесты, статический анализ.

Смысл в раннем обнаружении конфликтов. Чем дольше ветка живёт отдельно, тем больнее слияние; чем позже найдена ошибка, тем дороже исправление.

**2. Что такое CD?**

Аббревиатура покрывает два разных понятия.

**Continuous Delivery** — код после проверок всегда готов к выкатке, но решение о выкатке принимает человек. Это текущая схема проекта: `when: manual`.

**Continuous Deployment** — выкатка происходит автоматически, без подтверждения. Требует высокого доверия к тестам и отработанного отката.

**3. Зачем автоматизировать деплой?**

**Воспроизводимость.** Одна и та же последовательность шагов каждый раз. Человек пропускает шаги, путает порядок, забывает про промежуточную команду.

**Скорость.** Выкатка занимает минуту вместо получаса ручной работы.

**Отсутствие доступа к серверу.** Разработчику не нужен SSH на продакшен — он делает push, остальное выполняет система.

**Аудит.** Каждая выкатка привязана к коммиту, автору и времени, история сохраняется.

**Обязательность проверок.** Тесты выполняются всегда, а не когда о них вспомнили.

**4. Что происходит при падении теста в CI?**

Тестовый фреймворк возвращает ненулевой код завершения, задача помечается как проваленная, пайплайн останавливается. Последующие этапы получают статус `Skipped` и не выполняются.

Проверено на практике: при упавшем `test_404` этапы `build` и `deploy` пропущены. Коммит в истории отмечен красным — любой, кто откроет репозиторий, увидит, что на нём код сломан.

**5. Почему тесты должны выполняться до деплоя?**

Чтобы сломанный код не попал на сервер. Порядок этапов создаёт физический барьер: провалились тесты — деплой не запустится, независимо от чьего-либо желания.

Обратный порядок лишён смысла: узнавать о поломке после того, как её увидели пользователи, — не проверка, а констатация.

**6. Почему секреты нельзя коммитить в git?**

**История неизменяема.** Удалённый файл остаётся в предыдущих коммитах. Достать его оттуда может любой, у кого есть доступ к репозиторию.

**Репозиторий копируется.** Каждый клон, каждый форк, каждая резервная копия содержит полную историю со всеми секретами.

**Область доступа шире, чем кажется.** Доступ к коду имеет вся команда, CI-система, иногда подрядчики. Доступ к продакшен-базе должен иметь узкий круг.

**Ротация ломается.** Смена пароля требует правки в коде, коммита и выкатки — вместо изменения одного значения в настройках.

**7. Почему `latest` не всегда хороший тег?**

Разобрано в разделе Docker Image: старый образ теряет имя, версия перестаёт быть определённой, откат становится невозможным без заранее записанного ID.

Коротко: `latest` не идентифицирует ничего. Тег `7984be98` ведёт к конкретному коммиту.

**8. Как откатиться на старую версию?**

**При тегах по коммиту** — запустить контейнер из предыдущего образа:

```bash
docker run training-app:7984be98
```

Образ существует, имя известно, соответствие коду однозначное.

**Через git** — вернуть предыдущий коммит (`git revert`), запушить, дождаться пайплайна. Медленнее, но история остаётся линейной и понятной.

**Что нужно для отката в принципе:** осмысленные теги, сохранённые образы предыдущих версий, обратимые миграции базы. Последнее — самая частая причина, по которой откат оказывается невозможным.

**9. На что смотреть при падении пайплайна?**

**Какой этап упал** — по схеме пайплайна видно, где остановилось.

**Лог задачи, с конца.** Там текст ошибки и код возврата.

**Точная формулировка ошибки.** В этой работе три похожих сбоя подключения различались только текстом, и каждый указывал на свою стадию: не резолвится имя, отказ соединения, отказ аутентификации.

**Что изменилось с последнего успешного запуска.** Сравнение с предыдущим зелёным пайплайном сужает круг.

**На каком раннере выполнялась задача** — строка `Running on ...` в начале лога. Задача, ушедшая не на тот раннер, ведёт себя непредсказуемо.

**Состояние целевой системы**, если этап деплоя: `docker ps -a`, логи контейнеров. Лог задачи показывает только то, что видел раннер.

**10. Чем отличается автоматический деплой от ручного?**

**Автоматический** выполняется сразу после успешных предыдущих этапов. Быстро, без задержек, но любое слияние в основную ветку немедленно оказывается в продакшене.

**Ручной** (`when: manual`) создаёт задачу в состоянии ожидания и требует явного действия. Медленнее, зато момент выкатки выбирает человек, и решение принимается осознанно.

Технически различие в одной строке конфигурации. По сути — в том, кто отвечает за выкатку: система или человек.

## Useful Commands

**Локальная проверка тестов:**

```bash
python3 -m pytest tests/ -v
echo "код возврата: $?"
```

Форма `python3 -m pytest` не зависит от `PATH` — работает независимо от того, куда pip установил пакет.

**Запуск среды:**

```bash
docker compose up -d --build
docker compose ps
docker compose logs app --tail 20
```

**Проверка эндпоинтов:**

```bash
curl -i http://localhost:8080/
curl -i http://localhost:8080/health
curl -i http://localhost:8080/qwerty
```

**Диагностика раннера:**

```bash
sudo gitlab-runner list
sudo systemctl status gitlab-runner
sudo journalctl -u gitlab-runner -n 30 --no-pager
```

**Проверка секретов перед коммитом:**

```bash
git status --untracked-files=all
git check-ignore -v .env
```

Вторая команда выводит правило, по которому файл игнорируется. Пустой вывод и код возврата 1 означают, что файл **не** игнорируется.
