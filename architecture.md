# Архитектура

Кто что выполняет и почему схема устроена именно так.

---

## Общая схема

```
Разработчик
    │ git push
    ▼
┌─────────────────────────────┐
│ GitLab (gitlab.com)         │
│ • хранит код                │
│ • раздаёт задачи раннерам   │
│ • содержит Container Registry│
│ • НИЧЕГО НЕ ВЫПОЛНЯЕТ       │
└──────────┬──────────────────┘
           │ раннер сам запрашивает задачи
           ▼
┌─────────────────────────────┐
│ Runner host (intern-srv-l2) │
│ • процесс gitlab-runner     │
│ • докер-демон               │
│ • создаёт контейнеры задач  │
└──────────┬──────────────────┘
           │ создаёт под каждую задачу
           ▼
┌─────────────────────────────┐
│ Контейнер задачи            │
│ • временный, удаляется      │
│ • свежий клон репозитория   │
│ • команды script выполняются│
│   ЗДЕСЬ                     │
└──────────┬──────────────────┘
           │ SSH (для deploy)
           ▼
┌─────────────────────────────┐
│ Deployment server           │
│ • докер-демон               │
│ • SSH-сервер                │
│ • контейнер приложения      │
└──────────┬──────────────────┘
           │ docker pull
           ▼
      Container Registry
```

## Ответы на вопросы задания

| Вопрос | Ответ |
|---|---|
| Где работает GitLab? | На стороне Anthropic... точнее, на серверах GitLab (gitlab.com). Хранит код и координирует, сам ничего не выполняет |
| Где работает GitLab Runner? | На `intern-srv-l2` как системный сервис `gitlab-runner` |
| Где Docker executor создаёт контейнеры? | На том же хосте — обращается к докер-демону машины, где сам находится |
| Где собирается образ? | Внутри контейнера `docker:dind`, поднятого как сервис рядом с задачей |
| Где хранится образ? | В GitLab Container Registry |
| Где происходит развёртывание? | На deployment server, команды приходят по SSH |
| Какой машине нужен Docker? | Runner host (создавать контейнеры) и deployment server (запускать приложение) |
| Какой машине нужен SSH? | Контейнеру задачи `deploy` — клиент; deployment server — сервер |
| Кому нужен доступ к реестру? | Задаче `build-image` на запись, deployment server на чтение |

## Частный случай этой установки

Машины 2 и 3 — **физически одна и та же**: `intern-srv-l2`. Раннер стоит там же, куда идёт развёртывание.

Логически они всё равно разделены: задача выполняется в изолированном контейнере, не имеющем доступа к докер-демону хоста, и подключается к нему по SSH как к внешней машине. Адрес `172.17.0.1` — шлюз сети `docker0`, через который контейнер видит свой хост.

В общем случае это разные серверы, и схема от этого не меняется.

---

## Почему раннер стоит на сервере, а не в облаке

Сервер находится в частной сети университета и не имеет публичного адреса. Облачные раннеры GitLab до него не достучатся: NAT пропускает исходящие соединения, но не входящие.

**Направление перевёрнуто.** Раннер сам устанавливает исходящее соединение с gitlab.com и опрашивает: есть ли работа. Получив задачу, выполняет её локально.

Ни проброса портов на роутере, ни открытого наружу SSH — ничего, что требовало бы согласования с администраторами сети.

Именно поэтому раннер называют агентом: он **тянет** задачи к себе, а не ждёт, пока их пришлют.

---

## Три уровня, которые нельзя путать

Разделение принципиально, и большая часть ошибок в CI растёт из его непонимания.

**GitLab** — координатор. Знает про пайплайны, хранит артефакты и переменные, но не выполняет ни одной команды из `script`.

**Runner host** — машина с процессом `gitlab-runner`. При executor `shell` команды выполняются прямо здесь. При executor `docker` — здесь только создаются контейнеры.

**Контейнер задачи** — изолированное окружение с собственным пространством имён. Своя файловая система, свои процессы, свой hostname. Уничтожается после завершения задачи вместе со всем, что внутри.

Доказательство разделения — в `docs/runner.md`.

---

## Почему deploy требует SSH

Контейнер задачи изолирован от хоста: у него нет доступа к докер-демону сервера, к его файловой системе, к работающим там контейнерам.

Но развёртывание по определению меняет состояние сервера — останавливает старый контейнер, запускает новый.

**Изоляция противоречит задаче**, поэтому нужен канал наружу. SSH и есть этот канал: задача подключается к серверу как обычный клиент и выполняет команды там.

Альтернатива — executor `shell`, где команды сразу идут на хосте. Так был устроен деплой в предыдущем задании. Но `shell` даёт задаче полный доступ к машине, а это ослабление изоляции для всех задач, включая тесты и сборку.

Docker executor + SSH разделяет: изоляция по умолчанию, доступ только там, где он нужен, и только через явно настроенный ключ.

## Поток образа

```
build-image (контейнер задачи)
    │ docker build внутри dind
    ▼
образ существует только в контейнере dind
    │ docker push
    ▼
Container Registry ─────────┐
                            │ docker pull
                            ▼
                    deployment server
                            │ docker run
                            ▼
                    работающее приложение
```

**Реестр здесь не формальность.** Контейнер `dind` живёт ровно столько, сколько идёт задача — минуту. Собранный образ исчезнет вместе с ним.

Без публикации в реестр развёртывать было бы нечего: деплою пришлось бы собирать приложение заново из исходников, и тогда артефакт, прошедший сборку, никто бы не использовал.

Реестр делает образ независимым от машины, где он собран, и достижимым откуда угодно. Отсюда же возможность отката: старые образы остаются доступны.

## Что нужно каждому участнику

| Участник | Docker | SSH | Реестр | Ключ |
|---|---|---|---|---|
| GitLab | — | — | хранит | — |
| Runner host | демон | — | — | — |
| Контейнер `build-image` | клиент + dind | — | запись | — |
| Контейнер `deploy` | — | клиент | — | приватный |
| Deployment server | демон | сервер | чтение | публичный |

**Минимальные привилегии.** Учётные данные реестра для сборки генерируются GitLab на время задачи и действуют только пока она идёт. SSH-ключ создан отдельно от личного ключа разработчика и используется только для развёртывания.
