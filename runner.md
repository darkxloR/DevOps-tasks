# GitLab Runner

Что это, как настроен, и экспериментальное доказательство, где выполняется задача.

---

## Что такое GitLab Runner

Процесс-агент, выполняющий задачи пайплайна. Устанавливается отдельно от GitLab, регистрируется в проекте и опрашивает сервер: есть ли работа.

Ключевое: раннер **сам подключается** к GitLab исходящим соединением. Благодаря этому он работает за NAT, без публичного адреса и проброса портов.

---

## Executor

Executor определяет, **где** выполняются команды из `script`.

| Executor | Где выполняется | Изоляция | Для чего |
|---|---|---|---|
| `shell` | прямо на машине раннера, от пользователя `gitlab-runner` | нет | развёртывание, управление хостом |
| `docker` | во временном контейнере | полная | тесты, сборка |
| `kubernetes`, `docker+machine` и др. | в кластере / динамических ВМ | — | масштабные установки |

### Почему в этом проекте `docker`

Задание требует явно. Но требование осмысленное:

**Изоляция.** Тесты и сборка не зависят от того, что установлено на сервере, и ничего там не оставляют. Каждый запуск начинается с чистого окружения.

**Воспроизводимость.** Версия Python берётся из образа, а не из системы. Обновление сервера не ломает пайплайн.

**Безопасность.** С `shell` любой, кто может изменить `.gitlab-ci.yml`, выполняет произвольную команду на сервере. С `docker` — только внутри временного контейнера.

**Цена** — деплой перестаёт быть тривиальным. Контейнер не дотянется до докер-демона хоста, поэтому нужен SSH.

### Сравнение на одной машине

На `intern-srv-l2` зарегистрированы **два раннера**:

```
intern-srv-l2   Executor=shell    (из предыдущего задания)
intern-srv-l2   Executor=docker   tag: docker-build
```

Один `gitlab-runner` обслуживает обе регистрации. Задачи направляются метками: всё в этом проекте помечено `docker-build`.

## Установка и регистрация

```bash
curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
sudo apt install gitlab-runner
sudo gitlab-runner register --url https://gitlab.com --token glrt-XXXX
```

Ответы: имя раннера, executor `docker`, образ по умолчанию `docker:27`.

### Регистрация обязательно с sudo

Первая попытка выполнялась без него, и конфигурация легла в `~/.gitlab-runner/config.toml`. Системный сервис читает `/etc/gitlab-runner/config.toml` — раннер числился зарегистрированным, но задач не получал.

Проверяется так:

```bash
sudo gitlab-runner list    # ConfigFile=/etc/gitlab-runner/config.toml
gitlab-runner list         # ConfigFile=/home/USER/.gitlab-runner/config.toml
```

Если раннер виден только во второй команде — он не работает как сервис.

### Привилегированный режим

```toml
[runners.docker]
  tls_verify = false
  image = "docker:27"
  privileged = true
```

Нужен, чтобы внутри задачи мог запуститься `docker:dind`. Без привилегий вложенный `dockerd` не создаёт пространства имён и cgroups — стартует и сразу падает.

**Цена.** Привилегированный контейнер имеет расширенный доступ к ядру хоста, это ослабление изоляции. Осознанный компромисс для учебной среды; в production применяют Kaniko или BuildKit, которые собирают образы без привилегий.

### Метки

```yaml
tags:
  - docker-build
```

Метка направляет задачу на конкретный раннер. У раннера с `shell` её нет, поэтому задачи проекта на него не попадают.

Галка **Run untagged jobs** у docker-раннера снята намеренно: иначе он перехватывал бы задачи без меток, и было бы непонятно, что где выполнялось.

## Эксперимент: где выполняется задача

Диагностическая задача `runner-info` собирает информацию об окружении.

### Процессы

```
$ ps aux
PID   USER     TIME  COMMAND
    1 root      0:00 /bin/sh
   19 root      0:00 /bin/sh
   26 root      0:00 ps aux
```

**Три процесса.** На хосте их сотни. Первый имеет **PID 1** — признак отдельного пространства имён процессов: внутри контейнера главный процесс видит себя первым в системе.

Формат вывода урезанный (`PID USER TIME COMMAND` вместо привычных колонок) — это BusyBox из Alpine, на котором собран образ `docker:27`. Полноценного `procps` там нет.

### Hostname

Внутри задачи он вида `runner-attcco-yc-project-86095748-concurrent-0`, на сервере — `intern-srv-l2`. Разные значения.

### Рабочий каталог

```
$ pwd
/builds/tikokhlghatyan/traning-app-ci

$ ls -la
drwxrwxrwx  .git
-rw-rw-rw-  .gitignore
-rw-rw-rw-  .gitlab-ci.yml
-rw-rw-rw-  Dockerfile
drwxrwxrwx  src
drwxrwxrwx  tests
```

Свежий клон репозитория. В логе сборки видно:

```
Created fresh repository.
Checking out b8bdca70 as detached HEAD
```

Каждая задача получает чистую копию — ничего от предыдущих.

### Вывод

Задача выполняется **в контейнере**, не на хосте. Четыре независимых подтверждения: число процессов, PID 1, отличающийся hostname, свежий клон.

Контейнер создаётся **докер-демоном хоста** — раннер работает на сервере, других демонов у него нет.

## Эксперимент: где находится Docker

Три состояния, каждое со своим сообщением об ошибке.

### 1. Без сервиса dind

```yaml
runner-info:
  image: docker:27
  script:
    - docker version
```

```
Client:
 Version: 27.5.1
 ...
error during connect: Get "http://docker:2375/v1.47/version":
dial tcp: lookup docker on 10.0.10.1:53: no such host
```

**Клиент есть, демона нет.** Клиент напечатал свою версию — он входит в образ. До демона не достучался: имя `docker` не резолвится, потому что сервиса с таким именем не существует.

Заметь: клиент **уже настроен** искать демон по адресу `http://docker:2375`. Это переменная `DOCKER_HOST`, которую подставляет сам раннер из `config.toml`.

### 2. Сервис есть, TLS включён

```yaml
  services:
    - docker:27-dind
```

```
Cannot connect to the Docker daemon at tcp://docker:2375.
Is the docker daemon running?
```

**Ошибка изменилась.** Теперь имя резолвится — сервис поднят, контейнер создан. Но демон не отвечает на порту 2375.

Причина: свежие версии dind по умолчанию поднимают демон **с шифрованием на порту 2376**, а клиент стучится на 2375 без TLS.

### 3. TLS отключён

```yaml
  variables:
    DOCKER_TLS_CERTDIR: ""
```

```
Client:
 Version: 27.5.1
Server: Docker Engine - Community
 Engine:
  Version: 27.5.1
 containerd:
  Version: v1.7.25
 runc:
  Version: 1.2.4
 docker-init:
  Version: 0.19.0
```

**Секция `Server:` появилась.** Демон отвечает, виден весь стек: Engine, containerd, runc.

### Таблица различий

| Конфигурация | Сообщение | Стадия сбоя |
|---|---|---|
| без `services` | `no such host` | имя не резолвится |
| `dind`, TLS включён | `Cannot connect` | имя есть, порт не отвечает |
| `dind` + `DOCKER_TLS_CERTDIR: ""` | `Server:` в выводе | работает |

Различение по тексту ошибки — рабочий навык: каждое сообщение указывает на свою ступень.

## Где физически собирается образ

Внутри контейнера `docker:27-dind`, поднятого как сервис. Это **не** докер-демон хоста.

Следствия:

**Кеш слоёв не сохраняется** между запусками — каждая сборка с нуля. Медленнее, зато предсказуемо.

**Собранный образ живёт минуту** и исчезает вместе с контейнером сервиса. Поэтому обязателен `docker push` в реестр: иначе развёртывать было бы нечего.

**Альтернатива** — пробросить сокет хоста (`/var/run/docker.sock`) внутрь контейнера задачи. Тогда сборка идёт на хосте, кеш сохраняется, образ остаётся локально. Но задача получает полный доступ к докеру хоста, что равнозначно root.

В этом проекте выбран dind: изоляция важнее скорости сборки.

## Очистка после задач

Docker executor удаляет контейнер задачи и связанные сервисы автоматически. В логе это видно:

```
Container runner-attcco-yc-project-...-docker-0 disconnected from network bridge
Cleaning up project directory and file based variables
```

Образы, скачанные раннером (`docker:27`, `alpine:latest`, `postgres:16`), остаются на хосте и переиспользуются. Со временем накапливаются — на рабочем сервере стоит настроить периодическую очистку:

```bash
docker image prune -a --filter "until=168h"
docker builder prune
```

Кеш сборки живёт отдельно от образов и не удаляется вместе с ними.

## Диагностика

```bash
sudo gitlab-runner list                            # зарегистрированные раннеры
sudo systemctl status gitlab-runner                # состояние сервиса
sudo journalctl -u gitlab-runner -n 30 --no-pager  # журнал
sudo cat /etc/gitlab-runner/config.toml            # конфигурация
```

**Задача висит в `Pending`** — раннера с нужной меткой нет, либо он офлайн. Проверить метки в Settings → CI/CD → Runners.

**Задача ушла не на тот раннер** — смотреть первую строку лога: `Running on <имя> ...`.

**Токены при выводе конфигурации** видны открытым текстом. Перед копированием в документацию или переписку:

```bash
sudo gitlab-runner list 2>&1 | sed 's/Token=[^ ]*/Token=***/'
```
