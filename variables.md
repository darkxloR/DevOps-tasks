# Переменные

Откуда берутся значения, как передаются между задачами и доходят до приложения.

---

## Путь переменной

```
GitLab CI/CD Variables  ─┐
.gitlab-ci.yml          ─┼─►  окружение задачи  ─►  docker run -e  ─►  контейнер  ─►  приложение
предопределённые GitLab ─┤
dotenv из прошлой задачи─┘
```

Четыре источника сливаются в одно окружение задачи. Дальше значения передаются явно — через флаги `-e` команды `docker run`.

---

## Пять видов переменных

Задание требует различать их. Разница не терминологическая: у каждого вида своя область видимости и свой жизненный цикл.

### 1. Переменные в `.gitlab-ci.yml`

```yaml
run-tests:
  variables:
    POSTGRES_DB: appdb
    POSTGRES_PASSWORD: testpass
    BASE_URL: http://localhost:9000
```

**Видны** внутри задачи, где объявлены. Можно объявить и глобально — тогда во всех задачах.

**Хранятся в git**, доступны всем, кто видит репозиторий. Годятся только для несекретных значений.

**Пароль тестовой базы здесь задан намеренно.** База создаётся на минуту внутри изолированной сети задачи, порт наружу не проброшен, после завершения уничтожается. Этим паролем нельзя воспользоваться — объекта уже не существует.

### 2. Переменные проекта (GitLab CI/CD Variables)

Settings → CI/CD → Variables.

| Переменная | Тип | Masked | Protected | Назначение |
|---|---|---|---|---|
| `SSH_PRIVATE_KEY` | File | нет | нет | ключ для подключения к серверу |
| `DEPLOY_DB_PASSWORD` | Variable | да | нет | пароль базы на сервере |
| `DEPLOY_HOST` | Variable | нет | нет | адрес сервера |

**Не в git.** Хранятся на стороне GitLab, подставляются в окружение задачи при запуске.

**Masked** скрывает значение в логах, заменяя на `[MASKED]`. Требования: минимум 8 символов, без пробелов и переводов строк, одна строка.

**Protected** — переменная доступна **только в защищённых ветках**. Подробнее ниже, это стоило двух сбоев.

**Type: File** — GitLab записывает значение во временный файл и подставляет **путь** к нему. Нужен для многострочных значений вроде SSH-ключа.

### 3. Предопределённые переменные GitLab

Подставляются автоматически, все начинаются с `CI_`.

```
$ env | grep CI_REGISTRY
CI_REGISTRY=registry.gitlab.com
CI_REGISTRY_IMAGE=registry.gitlab.com/tikokhlghatyan/traning-app-ci
CI_REGISTRY_USER=gitlab-ci-token
CI_REGISTRY_PASSWORD=[MASKED]
```

| Переменная | Что содержит |
|---|---|
| `CI_REGISTRY` | адрес реестра |
| `CI_REGISTRY_IMAGE` | полный путь к образам проекта |
| `CI_REGISTRY_USER` / `CI_REGISTRY_PASSWORD` | учётные данные, действуют только пока идёт задача |
| `CI_COMMIT_SHORT_SHA` | короткий SHA коммита — используется как тег образа |
| `CI_COMMIT_SHA` | полный SHA, 40 символов |
| `CI_COMMIT_BRANCH` | имя ветки |

**`CI_REGISTRY_PASSWORD` замаскирован автоматически** — это встроенное поведение, настраивать не нужно. Остальные три показаны как есть: адрес и логин `gitlab-ci-token` секретами не являются.

Прямое следствие: требование «не хардкодить учётные данные реестра» выполняется само — хранить их нигде не приходится.

**Посмотреть все:**

```yaml
script:
  - env | grep CI_ | sort
```

Быстрее, чем искать в документации, и сразу с реальными значениями.

### 4. Переменные из предыдущей задачи (dotenv)

Задача `build-image` определяет тег и передаёт его дальше:

```yaml
script:
  - echo "IMAGE_TAG=$CI_COMMIT_SHORT_SHA" >> build.env
  - echo "IMAGE_NAME=$CI_REGISTRY_IMAGE" >> build.env
artifacts:
  reports:
    dotenv: build.env
```

Задача `deploy` получает их как обычные переменные окружения — ничего дополнительно объявлять не надо.

Механизм разобран ниже отдельно.

### 5. Переменные окружения контейнера

```bash
docker run -d --name training-app \
  -e DB_HOST=postgres \
  -e DB_NAME=appdb \
  -e DB_USER=appuser \
  -e DB_PASSWORD=$DEPLOY_DB_PASSWORD \
  -e APP_ENV=training \
  $IMAGE_NAME:$IMAGE_TAG
```

**Граница между окружением задачи и окружением приложения.** Переменные задачи не попадают в контейнер автоматически — их нужно передать явно флагом `-e`.

Справа от `=` стоят значения, которые уже развёрнуты на стороне задачи. Внутрь контейнера уходит результат.

Приложение читает их:

```python
db_host = os.environ.get("DB_HOST", "postgres")
db_password = os.environ.get("DB_PASSWORD", "")
```

Второй аргумент — значение по умолчанию. У пароля дефолт пустой намеренно: реальное значение в коде оказалось бы в git.

## Как работает dotenv

**Задача 1** создаёт файл вида `КЛЮЧ=значение` и объявляет его артефактом типа `dotenv`.

**GitLab** в конце задачи читает файл, разбирает пары и сохраняет их на своей стороне.

**Задача 2** получает эти пары в окружение при запуске.

### Эксперимент

Задача `check-vars` проверяет, что именно пересекает границу между задачами:

```yaml
check-vars:
  stage: deploy
  script:
    - echo "IMAGE_NAME=$IMAGE_NAME"
    - echo "IMAGE_TAG=$IMAGE_TAG"
    - ls -la
    - cat build.env || echo "build.env not found"
```

Результат:

```
IMAGE_NAME=registry.gitlab.com/tikokhlghatyan/traning-app-ci
IMAGE_TAG=51443c7c
--- files from previous job ---
drwxrwxrwx  .git
-rw-rw-rw-  .gitignore
-rw-rw-rw-  .gitlab-ci.yml
-rw-rw-rw-  Dockerfile
drwxrwxrwx  src
drwxrwxrwx  tests
cat: can't open 'build.env': No such file or directory
build.env not found
```

**Переменные пришли. Файла нет.**

При том, что в `build-image` файл точно существовал — иначе GitLab не смог бы его прочитать.

### Что это доказывает

| Вопрос | Ответ |
|---|---|
| Job 2 в том же контейнере? | Нет — разный hostname, свежий клон, файлы не переносятся |
| Наследует окружение Job 1? | Нет — обычные переменные оболочки не переживают границу |
| Что переживает? | Только объявленное артефактами |
| Как работает dotenv? | GitLab читает файл, сохраняет пары у себя, подставляет в следующие задачи |
| Что с файлами Job 1? | Уничтожаются вместе с контейнером |

**Ключевое: передаётся не файл, а его содержимое**, разобранное GitLab. Файл — формат передачи, посредник. После прочтения он не нужен.

Этим `reports: dotenv` отличается от обычных артефактов: те действительно копируются в следующую задачу как файлы.

### Зачем это нужно

Задание запрещает вычислять тег независимо в каждой задаче.

Пока тег равен `$CI_COMMIT_SHORT_SHA`, оба вычисления дадут одно значение. Но логика может усложниться — тег с датой, номером пайплайна, суффиксом ветки. Тогда две формулы разойдутся, и развернётся не тот образ, который собрали.

Ошибка была бы тихой: пайплайн зелёный, образ существует, приложение работает — просто не той версии.

Одна задача определяет значение, остальные получают. Источник истины единственный.

## Приоритет переменных

Переменные проекта **перекрывают** объявленные в `.gitlab-ci.yml`.

Это стоило сбоя в предыдущем задании: в задаче было прописано `DB_PASSWORD: testpass`, в настройках проекта — другое значение. База создавалась с одним паролем, приложение подключалось с другим.

**Практическое следствие.** Имена переменных проекта и переменных пайплайна не должны пересекаться, если они означают разное.

В этом проекте разведено намеренно:

| Переменная | Где | Для чего |
|---|---|---|
| `DB_PASSWORD` | `.gitlab-ci.yml` | временная база в тестах |
| `DEPLOY_DB_PASSWORD` | настройки проекта | реальная база на сервере |

Разные имена — конфликта нет, и видно, что относится к тестам, а что к продакшену. Это и есть разделение конфигурации сборки и конфигурации приложения.

## Protected: ловушка, стоившая двух сбоев

Галка **Protected** означает, что переменная доступна **только в защищённых ветках**. По умолчанию защищена `main`; feature-ветки — нет.

### Сбой 1: тесты

`DB_PASSWORD` была помечена Protected. В ветке `feature/gitlab-cicd` она не пришла — подставилась пустая строка.

Цепочка последствий:

```
переменная пуста
  → POSTGRES_PASSWORD пустой
  → postgres отказывается стартовать
  → порт 5432 не отвечает
  → приложение падает при init_db()
  → тесты: Connection refused
```

Пять ступеней между настройкой галки и симптомом. По тексту ошибки видна последняя, причина — на первой.

### Сбой 2: деплой

`DEPLOY_HOST` с той же галкой:

```
ssh: Could not resolve hostname : Name does not resolve
                                ↑ пусто
```

Между словом `hostname` и двоеточием пустота — адреса не было.

### Как диагностировать

```yaml
script:
  - echo "DEPLOY_HOST=[$DEPLOY_HOST]"
  - echo "password length: ${#DB_PASSWORD}"
```

Квадратные скобки показывают границы значения: пустая переменная выведется как `[]`.

`${#VAR}` даёт **длину** строки, не раскрывая её — безопасный способ проверить секрет.

### Когда Protected уместна

Для переменных, которые не должны попадать в feature-ветки: продакшен-секреты, ключи от боевых серверов.

Логика в том, что любой участник может создать ветку и написать в пайплайне `echo $SECRET`. Protected не даст этого сделать вне защищённых веток.

В учебном проекте галки сняты, потому что работа идёт в feature-ветке. В реальном — защищённой делается `main`, а развёртывание в продакшен запускается только оттуда.

## Безопасность

**Секреты не в git.** `.gitignore` заведён до первого коммита:

```
.env
*.log
__pycache__/
```

Проверка перед коммитом:

```bash
git status --untracked-files=all    # показывает каждый файл отдельно
git check-ignore -v .env            # какое правило сработало
```

Первая команда важна: без флага git показывает новый каталог одной строкой, и содержимое не видно.

**В репозиторий коммитится `.env.example`** — структура без значений.

**Секреты не в логах.** GitLab маскирует переменные с галкой Masked и предопределённые секреты. Но маскирование не покрывает всё:

- значение может попасть в лог через вывод команды, которая его печатает
- многострочные значения маскировать нельзя

Практический случай из этой работы: приватный SSH-ключ попал в лог через сообщение об ошибке `cp: unrecognized option: ---BEGIN OPENSSH PRIVATE KEY-----`. Команда получила содержимое ключа вместо пути и вывела его целиком. Ключ пришлось пересоздать.

Вывод: секрет утекает не только через git, но и через сообщения об ошибках, вывод диагностических команд, переписку и скриншоты.

**Минимальные привилегии.** SSH-ключ создан отдельно от личного ключа разработчика, без парольной фразы (задача не сможет ввести её интерактивно), с комментарием `gitlab-ci-deploy` для опознания в `authorized_keys`.

Учётные данные реестра для сборки генерируются GitLab на время задачи и действуют только пока она идёт — хранить их не приходится вовсе.
